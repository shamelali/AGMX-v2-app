# HitPay serverless adapter

Deploy `api/hitpay/*.js` as Node serverless functions. Keep **all** credentials in server-only deployment variables (never a browser config file):

| Variable | Value |
| --- | --- |
| `HITPAY_API_KEY` | Business API key (sent as `X-BUSINESS-API-KEY` to HitPay). |
| `HITPAY_SALT` | **Per-webhook-endpoint** salt from Developers → Webhooks; not the API-key salt. |
| `HITPAY_WEBHOOK_URL` | Full public HTTPS `https://…/api/hitpay/webhook` URL, registered in the HitPay dashboard as an **event webhook** subscribing to `payment_request.completed` and `payment_request.failed`. |
| `HITPAY_API_BASE_URL` | Defaults to `https://api.hit-pay.com`; use `https://api.sandbox.hit-pay.com` for sandbox. HTTPS required (except local loopback tests). |
| `HITPAY_CURRENCY` | Three-letter uppercase code, defaults to `MYR`. The PocketBase invoices schema has no currency field; configure one currency per deployment. Amounts use two decimal places. |
| `PB_URL`, `PB_ADMIN_EMAIL`, `PB_ADMIN_PASSWORD` | PocketBase server URL and server-only superuser credentials. |

`POST /api/hitpay/create-payment` accepts **only** JSON `{ "invoiceId": "…" }` and `Authorization: Bearer <PocketBase user token>`. It refreshes the token, requires a tenant admin/secretary, verifies that the invoice belongs to that tenant, is unpaid/overdue, and has a valid whole-cent amount. It rejects invoices with any pending or succeeded payment, reserves a pending PocketBase `payments` record, calls `POST /v1/payment-requests`, checks the returned request ID, reference, amount, currency, status, and checkout URL, stores the request ID in `gatewayRef`, and returns `{ paymentId, requestId, url }`. The current PocketBase payment-method enum lacks `hitpay`: checkout is restricted to **card** and stored as method `card`, reference `hitpay`. No payment is marked paid from a browser redirect. A failed/uncertain create response leaves the reserved payment pending for reconciliation; do not automatically issue a second charge. A high-concurrency deployment should add an atomic per-invoice reservation/unique constraint before enabling concurrent checkout creation (the existing PocketBase list-and-create sequence alone cannot prevent two simultaneous requests).

`POST /api/hitpay/webhook` accepts the **dashboard event-webhook contract**, not the older per-request callback contract. HitPay's [webhook guide](https://docs.hitpayapp.com/apis/guide/events) says that event webhook requests have `Content-Type: application/json`, `Hitpay-Signature` containing a hex HMAC-SHA256 of the **exact raw JSON body bytes** keyed by the endpoint's own salt, and `Hitpay-Event-Object: payment_request` / `Hitpay-Event-Type: completed` or `failed` for the subscribed events. `_signature.js` is the isolated verifier: it rejects missing/malformed signatures and uses constant-time comparison of the 32-byte digest. No `sha256=` prefix, fallback headers, parsed/re-serialized payloads, or payload `hmac` are accepted. HitPay's **legacy** payment-request callback uses a different API-key salt and a sorted-parameter `hmac` field; for that reason creation does **not** pass HitPay's per-request `webhook` option. Register `HITPAY_WEBHOOK_URL` as an event webhook in the dashboard instead. If a serverless runtime pre-parses `req.body`, it **must** supply the original bytes as `req.rawBody` or leave the raw request stream readable; the endpoint fails closed if only a parsed object is available. Confirm raw-body delivery on the actual deployment before live use.

After signature verification, the webhook checks the payment request ID against the stored `gatewayRef` and the signed `reference_number` against the PocketBase payment ID, plus provider reference, method, tenant relationship, currency, amount, invoice amount, and state transitions. Only `completed` marks both payment and invoice paid; `failed` marks a pending payment failed while leaving the invoice unpaid. Duplicate deliveries do no writes. If the first database write succeeds and the second fails, a retry finishes the invoice. A webhook delivered before the create endpoint stores `gatewayRef` receives a non-2xx response for retry. Review unresolved pending payments, checkout/API failures, and provider delivery failures manually. Tests exercise the flow with mocked PocketBase/HitPay and no credentials: `node tools/test_hitpay_endpoints.js`.
